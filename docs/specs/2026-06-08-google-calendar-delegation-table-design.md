# サーバサイド設計根拠: カレンダー投影モデル

> 対象: `crowdodge` バックエンド（チーム「なせばなる」）
> ステータス: ドラフト v0.2 / 2026-06-08
> 確定仕様の所在: テーブル列・同期手段の仕様は docs リポジトリ（`table-definitions.md` / `google-calendar-sync.md`）。
> 本書の役割: 上記仕様が**そうである根拠**と、**サーバサイドでのみ必要な事項**を記す。クライアント側の取り決め（モバイルの Google 直読・端末キャッシュ等）は同期仕様書に従う前提とし、ここでは扱わない。

---

## 1. ドメイン思想（根拠）

**Calendar は外部の境界づけられたコンテキストであり、Source of Truth は Google である。**

- 本システムはカレンダーアプリではなく、カレンダー情報を消費する混雑回避アプリである。ゆえに「繰り返し（RRULE・シリーズ・例外展開）」は Calendar コンテキスト（Google）の内部事情とみなし、本システムのドメイン言語に持ち込まない。
- 境界に **ACL（腐敗防止層）** を置く根拠: Google の「マスタ＋RRULE＋例外インスタンス」モデルがドメインへ漏れ出すのを防ぎ、`singleEvents=true` で展開された個別予定（Occurrence）の平坦なストリームに翻訳して取り込むため。
- `events` を**投影（projection / 読み取りモデル）**とする根拠: カレンダーの真実は Google が所有するため、サーバは保持を「所有」ではなく「投影」と位置づける。投影はスコープが有限であり、これが近未来ローリング窓の必然的理由（容量都合ではない）。
- アプリ内編集を「Google へのコマンド送信＋再投影」とする根拠: アプリは Calendar のクライアントであって対抗するストアを持たない。これにより双方向編集と「Google が所有」が矛盾しない。

### コンテキストの重心

- `event` BC を **supporting context（同期/投影）** に軽量化する根拠: 予定の不変条件（start<end・例外対応など）は Google 側が保証するため、サーバ側にリッチな集約を置く必要がない。
- 真の Core ドメインは下流の **`EventDestination` / `EventCongestionPrediction` / `NotificationSchedule`**。これらは本システム独自の不変条件とビジネス価値（混雑予測・リマインド）を持つため、ここに設計の重心を置く。

## 2. テーブル設計の根拠（サーバ視点）

### events（個別予定の lean 投影）

- **繰り返し列（RRULE・終了日）を持たない根拠**: 繰り返しは Google が所有する概念であり、サーバは個別の発生回のみを扱う。発生回展開・例外マージ・無限窓問題を自前で抱えないため。
- **`recurring_event_id` / `original_start` / `etag` を持つ根拠**: ドメイン概念としてではなく**相関メタ**として。`recurring_event_id` は目的地のシリーズ共有ヒントと「それ以降すべて」編集のルーティング、`original_start` は編集スコープの分割点、`etag` は upstream 競合・無限ループの判定に必要。
- **`google_event_id` をキーとする根拠**: モバイルもサーバも Google から独立に導出するため、両者が調整なしに合意できる唯一の識別子が Google 自身の ID。外部所有エンティティを外部 ID で参照する。
- **保持フィールドを限定する根拠**: 混雑予測・目的地推定（LLM入力 = title/description/location）・リマインド（start/end/remind_timing）・通知本文（title）という**自社ドメインが消費する分だけ**を持つ。表示専用フィールドはモバイルが Google から直接取得するため、サーバが抱えると複製とドリフトのコストだけが残る。
- **`is_all_day` を持つ根拠**: 終日予定をパイプライン（混雑/通知）の対象外と判定するため。

### event_exceptions を持たない根拠

- 個別予定行そのものが1発生回であり、例外（時刻変更・中止・個別リマインド）は当該行の編集に吸収される。独立した訂正テーブルは不要。リマインドのフォールバックも `events.remind_timing → user_settings` の2段で足りる。

### event_destinations / event_destination_links（目的地のシリーズ共有）

- **シリーズで1グループを共有する根拠**: 目的地は場所に紐づき日付に依存しない（日付依存なのは混雑予測のみ）。同一シリーズの全発生回で目的地は同一になるため、高コストな推定（ルート計算・LLM）をシリーズで1回に抑える。
- **自前識別子＋ `recurring_event_id` 相関ヒント＋links に分ける根拠**: 1つのキー列に「自前 uuid」と「Google の ID」を混ぜると名前空間混在・型劣化・ライフサイクル結合（単発⇄シリーズ化で孤児化）が起きる。グループ識別子は自前 uuid（単一発行元）、`recurring_event_id` は重複判定用の外部相関ヒント列として分離する。メンバーシップを links に出すことで、1目的地:N発生回を downstream→up の参照方向のまま表現できる。

### event_congestion_predictions / notification_schedules（event_uuid 直参照）

- **`occurrence_start` 複合キーを廃し `event_uuid` 直参照にする根拠**: 1行＝1発生回となったため、発生回を識別する複合キー（`OccurrenceId`）が不要になり、単純な 1:1 参照で足りる。
- **混雑を 1予定=1行（`UNIQUE(event_uuid)`）とする根拠**: 発生回ごとに1つの混雑予測を要約して持ち、再予測は上書きで最新化する。

### user_calendars に同期・watch 状態を持つ根拠（サーバ専用）

- サーバは自社のエンリッチ（混雑/目的地/リマインド）のため Google を独自に同期し続ける必要がある。そのカーソル（`sync_token`）・窓の実体化端（`materialized_until`）・最終同期時刻・Push watch チャンネル状態を保持する。これらはサーバ運用専用で、クライアントには露出しない。

## 3. サーバ側同期運用（サーバ専用）

### ローリング窓の2系統同期（根拠）

- Google `events.list` は `syncToken`（増分）と `timeMin`/`timeMax`（期間）を併用できない（併用は400、トークン失効は410）。この制約があるため、増分同期（変更取り込み）と窓送り全同期（将来分の実体化）を分けて回す必要がある。
- 窓サイズ N を有界にする根拠: 1年先の混雑を今予測しても外部イベント情報が未確定で価値が薄く、日付接近時に再予測される。エンリッチの有効ホライズン＝近未来に窓を合わせる。

### 削除/中止時のサーバ側後処理

- Google で予定が削除/中止されたら、対応する投影行を除去し、`notification_schedules` は物理削除せず `status=cancelled`（監査・冪等性）。`event_destination_links` を除去し、メンバー不在となった目的地グループを掃除する。

### 書き込み仲介とループ防止（根拠）

- 書き込みをサーバ仲介とする根拠: ループ防止（自分の書き込みが webhook で戻る）と、編集後の再エンリッチを一貫して起動するため。`etag` で「前回取得版から変化したか」を判定する。

## 4. サーバ責務・横断事項

### エンリッチパイプライン

- `event` BC（同期/投影）が取り込んだ予定を起点に、ドメインイベントで下流を駆動する: 目的地推定 → 混雑予測 → 通知スケジュール。各 BC は自分のトランザクションをコミットし、次をイベントでトリガする（結果整合性）。
- `notification_schedules` は通知ジョブのキューであり、サーバが常時ポーリングして `notificate_time` 到来分を発火する。アンカーを自前 DB（`events`）に置くことで、通知発火時に Google へ問い合わせずに本文を構成できる。

### クォータの考え方

- Calendar API は無料でクォータ制のみ。モバイル＋サーバの2消費者が同一上流を別目的で読むが、双方とも増分同期のため定常コストは小さく、監視で足りる（スケール時に増枠検討）。
